### 评估方法

- **检索层**：复刻 `KBSearchTool` 的生产检索链路（`embed → hybrid search → rerank`），但保留**完整有序命中列表**，
  以便正确计算排序类指标（工具格式化后的 `sources` 按 cosine 排序，会丢失 rerank 顺序）。
- **端到端层**：**进程内直调真实 LangGraph**（与 `POST /api/chat` 同一套 `build_graph`），
  HTTP 路由相对该路径仅多出 JWT 鉴权、限流、SSE 封帧，三者不影响被测指标。
  延迟通过对 emit 事件流打时间戳分解：`t0 → tool_end(search_kb)` 为检索段，其后为生成段。

## 4. 检索层结果

### 4.1 检索质量（50 题，limit = 5）

| 指标 | @1 | @3 | @5 |
| --- | --- | --- | --- |
| **recall** | 0.880 | **1.000** | **1.000** |
| hit | 0.880 | 1.000 | 1.000 |
| nDCG | 0.880 | 0.956 | 0.956 |
| precision | 0.880 | 0.333 | 0.200 |

**MRR = 0.940**

> ⚠️ **precision@3 / @5 的读法**：本题库每题只有 **1 个**相关文档，且开启了文档级去重，
> 因此 `precision@3` 的理论上限就是 `1/3 = 0.333`、`precision@5` 是 `1/5 = 0.200`。
> 实测值 0.333 / 0.200 **恰好等于上限，即满分**。这两个数字不代表检索质量差，此处仅作记录，
> 判断检索质量应看 recall / hit / nDCG / MRR。

### 4.2 检索延迟（150 次采样 = 50 题 × 3 次重复）

| 阶段 | mean | p50 | p90 | p95 | min | max |
| --- | --- | --- | --- | --- | --- | --- |
| embed（查询向量化） | 189.4 | **100.3** | 263.0 | 356.6 | 78.1 | **4563.1** |
| search（Milvus hybrid） | 10.8 | **10.7** | 12.9 | 13.2 | 7.9 | 29.4 |
| rerank（cross-encoder） | 173.0 | 165.9 | 245.6 | 260.8 | 83.4 | 481.1 |
| **total** | 362.9 | **287.5** | 474.3 | **596.1** | 95.3 | 4679.0 |

- 本地向量检索（Milvus Lite hybrid）稳定在 **~11 ms**，完全不是瓶颈。
- 延迟几乎全部来自**外部 API 调用**（embed + rerank ≈ 95%）。
- `embed` 出现 1 次 **4563 ms** 离群点（上游网络抖动）。剔除该点后 mean ≈ 160 ms（实测 189.4 ms），
  即单点把均值抬高约 30 ms、并把 embed 的 max 抬到 4.6 s。
  **建议：看 p50/p90 而非 mean**。
- `rerank` 计数为 141 而非 150：命中不足 2 条时跳过 rerank（与生产逻辑一致）。

### 4.3 未命中 top-1 的 6 题（recall@1 = 0）

50 题中 6 题（12%）的首位命中不是标准答案，但**全部落在 top-2/3 内**。6 题呈现同一模式：

| 问题 | top-1 命中 | 标准答案 |
| --- | --- | --- |
| 优秀研究生奖学金的评审对象是哪些研究生？ | 优秀研究生奖学金评审和荣誉称号授予办法 | 研究生学生手册（2025版） |
| 直博生何时前无法继续博士学业可转硕？ | 研究生学生手册（2025版） | 学籍管理规定（东华研〔2022〕13号） |
| 非毕业年份思想品德优秀授予哪项荣誉称号？ | 优秀研究生奖学金评审和荣誉称号授予办法 | 研究生学生手册（2025版） |
| 研究生学籍管理规定的基本修业年限如何确定？ | 学籍管理规定（东华研〔2022〕13号） | 研究生学生手册（2025版） |
| 研究生旷课的处理流程是怎样的？ | 学籍管理规定（东华研〔2022〕13号） | 研究生学生手册（2025版） |
| 退学非定向研究生档案退回哪里？ | 学籍管理规定（东华研〔2022〕13号） | 研究生学生手册（2025版） |

**根因**：《研究生学生手册（2025版）》是一个 199 chunks 的汇编文档，内容与各专项管理规定**高度重叠**。
检索命中的「专项文件」在语义上确实是正确答案，只是数据集把汇编手册标为唯一 ground truth。

> 这是**数据标注口径问题，而非检索缺陷**。由于最终都进入 top-3，端到端侧未造成损失（引用命中率仍为 100%）。
> 若要严谨化，应支持**多文档标注**（一句话可同时由手册与专项文件回答）。

| 正确性 correctness | **0.948** |

### 5.2 引用准确性

| 指标 | 值 |
| --- | --- |

### 5.6 低分样本定位（4 例）

| 问题 | 忠实度 | 正确性 | 评委理由（节选） |
| --- | --- | --- | --- |
| 宿舍内允许使用哪些电器设备？ | **0.20** | 0.60 | 「事实性陈述没有在提供的资料中找到直接依据，但提供了获取信息的正确途径」 |
| 网络数据境外存储或提供有哪些法律后果和处罚措施？ | 0.60 | **0.20** | 「没有提供任何……具体信息，不能认为准确回答了用户问题」 |
| 东华大学研究生手册对学生社团指导教师有什么规定？ | 0.60 | 0.80 | 「未直接引用资料中的具体条款」 |
| 直博生何时前无法继续博士学业可转硕？ | 0.80 | 0.60 | 「转为硕士研究生培养的程序和条件未提供详细信息」 |

两类失败模式清晰：
1. **资料不足时模型自行发挥**（宿舍电器，忠实度 0.20）—— 检索未能提供依据，模型没有拒答而是编造了通行做法。
2. **资料中确有内容但未被利用**（社团指导教师、直博生转硕）—— 检索已命中，模型回答不完整或未引用具体条款。

> 这两类都不是检索问题，指向 **prompt 对「无依据时拒答」和「必须引用条款」的约束不足**。

### 5.7 延迟归因与优化实验（已回退）

为定位占 94.1% 的生成段，评测埋点新增三个时间戳（定义见第 9 节）：**末 token**、**流式生成（首→末）**、
**流式后收尾（末→结束）**。用 10 题做对照实验（与 50 题基线同一份数据集、同一评委模型）：

| 阶段（10 题，p50） | 值 |
| --- | --- |
| 检索段 | 442 ms |
| 首 token（TTFT） | 2658 ms |
| **流式生成（首→末）** | **7105 ms** |
| **流式后收尾** | **1.2 ms** |

**结论 1：框架/流式/后处理零开销，生成段 = 纯模型时间。**
收尾仅 1.2 ms；流式 7105 ms ÷ 118 token ≈ **60 ms/token（≈17 tok/s）**。
用同等规模提示词直连 BigModel 裸测可复现同一速率，确认瓶颈是 `glm-4-flash` 的**解码速度**，
而不是 LangGraph、SSE 封帧或 prompt 组装。

**结论 2：模型切换在现有 API 资源下不可行（已实测并否决）。**
尝试 `glm-4.5-flash` + 关闭其默认「思考」阶段 + 提示词压缩输出，两次独立 10 题运行均劣于基线：

| 指标 | 基线 `glm-4-flash` | `glm-4.5-flash` 第 1 次 | 第 2 次 |
| --- | --- | --- | --- |
| 首 token p50 | 2658 ms | 1959 ms | 4279 ms |
| 首 token max | 3991 ms | 17706 ms | 27206 ms |
| 总耗时 p50 | **9586 ms** | 11036 ms | 14948 ms |
| 输出 token / 轮 | 118 | 269 | 216 |
| faithfulness / correctness | 0.920 / 0.960 | 0.940 / 0.960 | 0.960 / 0.980 |

两个原因叠加：

1. `glm-4.5-flash` **话多约 2.3 倍**（216–269 vs 118 token），抵消了其约 2 倍的解码提速；
2. 该免费 key 上服务端**排队/限流**明显，反复出现 **15–27 s 首 token 毛刺**（基线最差仅 4.0 s）。

质量指标未退化，问题纯粹出在**延迟与稳定性**。

**处置：已回退。** `backend/` 生产代码与 `.env` 恢复原状（逐字节无 diff），
仅保留上述评测埋点；未采用任何延迟相关的生产改动。

**后续建议**：可控杠杆只有「更高吞吐的模型/额度」与「输出长度约束」两个，且必须**同时满足**才成立
——在解码速率提升前，压缩输出长度的收益会被模型话术变长抵消。检索侧不必再投入（仅占 4%）。

### 5.8 延迟优化、模型切换与记忆层开启（2026-10-01 落地）

第 5.7 节的结论是「解码吞吐是硬地板，换模型已被否决」。本轮先复核这个前提，再分两条线落地：
**代码侧消化可消除的开销**，**配置侧换掉吞吐地板**。

#### 5.8.1 复核：瓶颈定位与成本模型

对同一份提示词做归一化实测（`ms/token` 按 usage 返回的真实 `completion_tokens` 计算）：

| 请求形态 | ms/token |
| --- | --- |
| 基线形态（带 tool schema + 报告 skill 段） | 50.2 |
| 去掉 tool schema 与 skill 段 | 58.2 |
| 5 chunks → 3 chunks | 46.1 |
| 完全不注入 chunks | 53.1 |

**结论**：解码速率与请求形态无关，稳定在 **~46–58 ms/token（≈20 tok/s）**；prefill 仅约
**0.22 ms/token**。即生成段 ≈ `输出长度 × 46 ms` + 约 1.5 s 排队/网络。

这与 5.7「框架零开销、生成段 = 纯模型时间」一致，但给出了明确的成本模型：
**输出长度是乘数，模型吞吐是系数**——两者必须同时改善才成立，也解释了 5.7 中
`glm-4.5-flash` 为何「吞吐翻倍」却整体变慢。

#### 5.8.2 代码侧：消掉可消除的开销

| 改动 | 文件 | 效果 |
| --- | --- | --- |
| 报告 skill（工具 schema + ~700 token system 段）改为按需挂载 | `agent/graph.py`、`agent/prompts.py`、`agent/nodes.py` | **输入 4284 → 3578 token/轮（−16.5%）** |
| LLM SDK 客户端进程级复用（原本每请求新建 → 连接池重建） | `infra/llm.py` | 省每轮 DNS/TCP/TLS 握手 |
| 查询向量 LRU 缓存 | `infra/embedding.py` | 同一问题每轮被 embed 两次（KB 检索 + L2 记忆），第二次直接命中 |
| embed / rerank 软超时（15 s / 1.2 s），超时降级为第一阶段排序 | `infra/embedding.py`、`infra/reranker.py` | 削检索段长尾（本报告基线中 embed 曾出现 4563 ms 离群点） |
| `describe_collection` / `load_collection` 结果按 collection 缓存 | `infra/vector_store.py` | 每次查询省 2 次 RPC + 线程切换 |
| L1 / L2 / L4 记忆读取改为并发 | `agent/nodes.py` | 生产路径少两次串行 IO 等待 |
| `max_tokens` 2048 → 可配（默认 1024） | `agent/nodes.py`、`settings.py` | 仅约束长尾 |
| 修掉报告回放的人为 `sleep`（8 字符 / 20 ms） | `app.py` | 2000 字报告原会额外等待约 5 s |

新增配置集中在 `settings.py` 的 *Latency tuning* 段：`llm_max_tokens`、`llm_client_reuse`、
`kb_retrieval_limit`、`embed_timeout_ms`、`rerank_timeout_ms`、`rerank_overfetch_multiplier`/`_cap`、
`embedding_cache_size`、`kb_report_skill_gating`、`llm_extra_body`。

> ⚠️ **代码侧改动无法用墙钟单独证伪**：该端点抖动极大（同一请求实测 TTFT 在 249 ms ↔ 3561 ms 之间），
> 10 题样本下墙钟差异会被噪声吞没。可稳定观测的只有**输入 token（−16.5%）**与**检索段长尾收敛**。

#### 5.8.3 配置侧：换掉吞吐地板

换成 DeepSeek（`https://api.deepseek.com`，模型 `deepseek-flash`）。**踩到一个必现的坑**：

`deepseek-flash` 默认开启思考模式，而 agent 会把 assistant 消息回传给 API，思考模式要求把
`reasoning_content` 一并回传，否则整个请求 400：

```
400 - The `reasoning_content` in the thinking mode must be passed back to the API.
```

实测 5 种关闭参数，只有一种有效：

| 参数 | 结果 |
| --- | --- |
| `thinking: {"type": "disabled"}` | ✅ 生效（reasoning 归零） |
| `enable_thinking: false` | ❌ 仍在思考 |
| `thinking: false` | ❌ 422 反序列化失败 |
| `chat_template_kwargs` | ❌ 仍在思考 |

落地为**通用透传** `LLM_EXTRA_BODY`（默认空，不影响任何其它 provider），`.env` 中：

```ini
DEEPSEEK_BASE_URL=https://api.deepseek.com
LLM_DEFAULT_MODEL=deepseek-flash
LLM_COMPLEX_MODEL=deepseek-flash
LLM_EXTRA_BODY={"thinking": {"type": "disabled"}}
```

#### 5.8.4 50 题对照结果

同数据集、同 50 题（`optimized50.json`）。延迟对比（ms）：

| 阶段 | 基线 p50 | 现在 p50 | 基线 p95 | 现在 p95 | p50 改善 |

#### 5.8.5 评测器缺陷修复

本轮顺带修了两个会影响结论可信度的评测缺陷：

1. `eval/judge.py`：评委未继承 agent 的请求配置。思考 token 吃光 `max_tokens=256` 后返回空
   `content`，导致 **9/10 评委失败**，而报告仍显示满分（均值只统计了唯一成功的那条）——
   属于「静默失真」，比报错更危险。
2. `eval/run_agent_eval.py`：结果 JSON 不保存 `contexts`。离线重打分时评委看到「未检索到任何资料」，
   会得出严重偏低的分数（实测把 faithfulness 0.90 打成 0.38）。现已持久化。
3. `eval/retrieval.py`：本轮新增的查询向量缓存会被该评测器的 `--repeat N` 命中（同一 query 被重复
   测量），导致 embed 的 p50 显示为 **0.0 ms**，与基线不再可比。现改为每次测量前主动清缓存，
   测的是**冷启动成本**；同时把候选数倍率改为调用生产的 `overfetch_params()`，
   避免评测器与生产各存一份常量而悄悄漂移。

#### 5.8.6 结论与回退

- 端到端 **p50 11.5 s → 2.6 s（4.4×）**，**p95 21.5 s → 5.0 s（4.3×）**，同评委口径下质量持平。
- 剩余延迟构成（p50）：检索 607 ms（23%）/ LLM 首包 1010 ms（38%）/ 解码 927 ms（35%）。
  生成段已被压到 1.9 s 量级，**rank 1 的瓶颈重新回到检索段与首包**，但两者都在上游可控范围外
  （SiliconFlow embed/rerank 服务端抖动、模型服务端排队）。
- 长尾仅剩偶发单点（本轮 max 16.5 s），非系统性。
- **回退方式**：`backend/.env` 中 DeepSeek 四行与注释保留的智谱四行互换即可；
  代码侧改动与 provider 无关，可全部保留。

#### 5.8.8 候选池坍缩：为什么实际引用数常常不足 5

`kb_retrieval_limit = 5` 与 `grouping_enabled = true` 组合后，实际返回的参考文件数并不稳定为 5。
50 题实测分布：`5 个 → 30 题 · 4 → 4 · 3 → 6 · 2 → 7 · **1 → 3**`，平均 **4.02**。
逐阶段追踪（以两个极端样本为例）：

| 配置 | 「违法违纪处分」 | 「取消入学资格」 |
| --- | --- | --- |
| dense-only `limit=20` | 20 hits / **1** 个文档 | 20 hits / **2** 个文档 |
| hybrid `limit=20`（不分组） | 20 hits / **1** 个文档 | 20 hits / **2** 个文档 |
| hybrid `limit=20` + `group_by=doc_id` | **1** 个文档 | **4** 个文档 |
| hybrid `limit=12` + `group_by=doc_id` | 1 个文档 | **2** 个文档 |
| hybrid `limit=40` + `group_by=doc_id` | 2 个文档 | **10** 个文档 |

**根因**：`group_by_field` 是在**已截断的候选池之后**去重的。当前 `fetch_limit = limit × 4 = 20`，
而《研究生学生手册（2025版）》以 199/244 chunk 占语料 82%，相似度最高的 20 个候选几乎全来自它，
分组后自然只剩 1–2 个文档——工具于是只把 **1 个 chunk** 交给 LLM。

**影响**：
- 不是检索质量问题：recall@3 仍为 **1.000**（命中手册即命中标准答案）。
- 但**上下文比配置暗示的薄得多**：20/50 题拿不到 5 篇，3 题只拿到 1 个 chunk。
  这正好落在 5.6 的第二类失败模式上（「资料中确有内容但未被利用」），
  也解释了为什么答案有时不完整。
- `/api/chat` 返回给前端渲染的 `sources`（按 filename 去重）同样受此影响。

**修正方向**（未实施，需先验证）：分组开启时把候选池与 `limit` 解耦——例如
`fetch_limit = max(limit × 4, 60)`，让去重后有足够材料凑满 `limit` 个不同文档。
代价是 rerank 输入文档数上升（rerank 耗时随文档数近似线性，当前 p50 已达 440 ms），
因此必须同时评估延迟，不能只看多样性。

### 5.9 短期记忆效果评测（2026-10-01）

第 5.8.9 节只证明了记忆链路「能跑通」，没有回答「有没有用」——第 7 节一直把记忆列为评测盲区。
本节补齐基础设施并完成短期记忆的 A/B/C 对照实验。

#### 5.9.1 基础设施

| 文件 | 改动 |
| --- | --- |
| `eval/agent_eval.py` | `AgentRunner.run()` 新增 `history` / `conversation_id` / `user_id`（对齐 `app.py::_run_chat_session`），并新增 `capture_layers` 开关：用 `build_context_sections` 上的探针记录**哪些分层真的进了 prompt**，而不是从答案反推 |
| `eval/memory_eval.py`（新增） | 多轮会话模拟 + 埋点 case 构造 + 指标；会话模拟复刻 `routes.append_message` 的两个副作用（PG 落消息、记忆簿记），但把 `_memory_update` 从 fire-and-forget 改为 await 以保证下一轮状态确定 |
| `eval/run_memory_eval.py`（新增） | CLI 与报告输出 |

数据集落在 `eval/datasets/memory_short_term.jsonl`。

#### 5.9.2 实验设计

每个 case 是一条 6 轮会话：

1. **第 1 轮植入**：2 个随机代号（如 `SPKMKF-9850`、`TICKET-5559`）+ 1 条格式约束
   （「从现在起回答必须以【合规】开头」）。代号由固定种子随机生成——**不可能靠预训练知识或常识猜出**，
   所以答对只可能来自会话历史。
2. **3 轮无关 KB 问答**：把第 1 轮挤出 L5 窗口。3 是留了余量的最小值——压缩触发条件是
   `(总轮数 − 已压缩) − window ≥ batch`，window=2/batch=2 时 **2 轮就够**，每多一轮都要多花一次 agent 调用。
3. **2 个探针轮**：一个问代号（事实通道），一个问普通 KB 问题（约束通道）。

`window=2 / batch=2` ⇒ L4 收下第 1–4 轮，L5 只保留最后 1 轮（即探针轮）。

**为什么每 case 只植入 2 条事实**：加事实是同轮内零额外调用，看着像免费的分辨率旋钮，
但实测 4 条时 L4 保真度从 1.000 塌到 0.125（见 5.9.4 结论 4）——那时测的是**摘要容量**而非记忆通路。
所以这里固定 2 条，分辨率改由 case 数购买。

三组对照，同 case、同配置，只有「模型能看到什么」不同：

| 组 | window/batch | 传 ids | 含义 |
| --- | --- | --- | --- |
| A 记忆开启 | 2 / 2 | 是 | 第 1 轮只能经由 L4 到达 |
| B 记忆关闭 | 2 / 2 | 否 | 第 1 轮彻底不可见（= 第 2 节记录的基线） |
| C 全窗口 | 0 / 0 | 否 | 不裁剪、不压缩，第 1 轮逐字在 L5 —— **有效性上界** |

两个通道都用**确定性字符串匹配**（归一化后子串包含），不用 LLM 评委，因此可复现且免费。
另关闭 `MEMORY_AUTO_EXTRACT`，确保 L1/L2 为空——测量只反映短期记忆，不被长期记忆污染。

#### 5.9.3 结果（20 个 case × 3 组）

每个 case = 6 轮（1 植入 + 3 填充 + 2 探针）× 3 组 = **18 次 agent 调用**，
20 个 case 共 360 次，实测约 39 s/case。

| 组 | 约束遵守率 | 95% CI | 事实保留率 | 95% CI | case 级全对率 | 95% CI | 有 L4 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **A 记忆开启** | **0.250**（5/20） | [0.11, 0.47] | **0.700**（28/40） | [0.55, 0.82] | 0.700（14/20） | [0.48, 0.85] | 20/20 |
| B 记忆关闭 | 0.000（0/20） | [0.00, 0.16] | 0.000（0/40） | [0.00, 0.09] | 0.000（0/20） | [0.00, 0.16] | 0/20 |
| C 全窗口 | 0.550（11/20） | [0.34, 0.74] | 0.950（38/40） | [0.83, 0.99] | 0.950（19/20） | [0.76, 0.99] | — |

A 组 L4 侧指标：

- 事实保真度 **0.800**（32/40）—— 压缩后仍有八成植入事实存活于摘要
- L4 中记录到助手「我无法记忆」类免责声明的 case：**4/20**

> **CI 用 Wilson 区间**（小 n / 极端比例下正态近似会给出 <0 或 >1 的边界），
> 事实通道额外给出**以 case 为分母**的聚集稳健口径，因为同一 case 内的多个事实不独立。

#### 5.9.4 判读

**结论 1：case 有效，历史可见性是必要条件。**
两个通道上 C 都显著优于 B（CI 不重叠）。净增益 A − B = **+0.70**（事实）/ **+0.25**（约束）。

**结论 2：事实通道上，L4 的损失显著。**
A 0.70 vs C 0.95，CI 不重叠。而 A 组 L4 保真度是 0.80 —— 信息有八成在摘要里，
却只兑现了 0.70。**缺口来自「注入后没被用上」，不是压缩丢失**，
与 5.9.5 的拒答固化现象一致。

**结论 3：约束通道**无法判定**，且该指标天花板本身偏低。**
n=5 时曾得到 C=1.00 / A=0.20，并据此写下「L4 保不住指令」；**扩到 20 个 case 后
C 降到 0.55、A 为 0.25，两者 CI 重叠 —— 原结论不成立**。1.00 是小样本运气。

更值得注意的是天花板：**即使指令逐字躺在上下文里（C 组），5–6 轮之后遵守率也只有 0.55**。
说明模型对这个格式指令的遵守本身就不稳定，该指标的信噪比太低，
**不适合用来判定「记忆是否有损」**。它是"n=5 会骗人"的现成案例。

**结论 4（独立发现）：L4 摘要存在容量上限。**
把每 case 的植入事实从 2 条加到 4 条（同一轮内，**零额外 LLM 调用**），
L4 保真度从 1.000 塌到 **0.125**：摘要把 4 个编号压成「（编号 1 等）」，
因为 `_compress_rounds` 的目标是 **≤150 字**。

这与「2 条时保真度 1.000」不矛盾——那是**容量内**的表现，不是普遍保证。
产品含义：**用户在一轮里给出的标识符/编号越多，L4 丢得越多**；
本评测因此固定为 2 条（保持被测对象是记忆通路本身，而不是摘要容量），
样本量改用增加 case 数来买。

**结论 5：约束类信息仍应优先走长期记忆。**
本次为隔离短期记忆关闭了 `MEMORY_AUTO_EXTRACT`，那条格式约束只能靠 L4 承载。
生产配置下它会被关键词抽取 / L1 画像捕获（5.8.9 已验证 preferences 会进 L1），
以「用户偏好」的身份注入——**长期记忆不是可选项，它是承载用户约束的正确层级**。

#### 5.9.5 本轮修掉的缺陷（评测发现）

`eval/judge.py` 与三处生产 LLM 调用点**都没有传 `LLM_EXTRA_BODY`**：
`conversations/short_term_memory._compress_rounds`、`conversations/long_term_memory` 的抽取、
`skills/loader.invoke_skill`。

在默认开启思考的模型上，隐藏思考块会吃光 `max_tokens`，`message.content` 返回空字符串——
调用方看到的是「模型没返回内容」，于是**静默降级**而不是报错：

- 压缩返回空 → `maybe_compress` 不推进水位线（数据没丢，实现是对的），但那些轮次既不在 L5
  也不在 L4，**永久不可见**：修复前 5 个 case 里有 1 个完全没有 L4，事实保真度 0.80。

修复方式是新增 `infra/llm.with_extra_body(kwargs)` 统一注入，并把 4 个调用点全部改为走它。
修复后**同一实验**：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| L4 有摘要的 case | 4/5 | **5/5** |
| L4 事实保真度 | 0.800 | **1.000** |
| A 组事实保留率 | 0.200 | **0.600** |

> ⚠️ **样本量教训（本节的直接产出）**：L4 覆盖率与保真度是**确定性**指标，修复结论由它们确证。
> 但行为类指标绝不能靠 5 个 case 下结论——首轮 5 个 case 的配置给出了
> 「C 约束遵守率 = 1.000、A = 0.200，故 L4 保不住指令」，**扩到 20 个 case 后变成 C = 0.55、A = 0.25
> 且 CI 重叠，结论被推翻**（见 5.9.4 结论 3）。所有行为类结论都应带 CI，并以 CI 是否重叠作为判据。
>
> 当前 20 个 case 下：事实通道已可判定（CI 不重叠），**约束通道仍不可判定**
> （A 与 C 的 CI 重叠）。要把约束通道也收紧到可判定，需要更大的 n 或者一个信噪比更高的约束探针。

## 6. 关键发现

1. **端到端延迟瓶颈是 LLM 生成，不是检索。**
   生成段占 p50 总耗时的 94.1%，检索仅 4.0%。把检索优化到 0 也只能改善约 4% 的体感。
   降低延迟应针对：生成时长（输出长度控制 / 更快模型 / 流式首包优化），而非向量检索。
   埋点增强后的实测归因与已否决的优化尝试见 **5.7 节**。
   → **2026-10-01 已落地**：按此方向优化后 p50 11.5 s → 2.6 s，见 **5.8 节**。
   检索段在优化后的 p50 中回升到 23%，但在上游可控范围外。

2. **用户等待感的主要来源是 LLM 首包延迟。**
   TTFT p50 = 2.85 s，其中检索只占 0.46 s，**LLM 首包约 2.39 s**。
   → **2026-10-01**：换用 `deepseek-flash` 后 TTFT p50 = 1.62 s。

3. **「检索 → 引用」链路已饱和，错误转移到生成环节。**
   检索 recall@3 = 100% → 引用命中率 100% → 正确率 98% / 忠实度 92%。
   继续投入检索优化的收益已很低（且本地检索本来就只有 11 ms）。

4. **6/50 题的 top-1 偏差源于标注口径，不是检索缺陷。**
   全部由「汇编手册 vs 专项文件」的内容重叠造成，且都落在 top-3 内，未影响端到端结果。
   → 数据集应支持多文档标注。

5. **成本极低但输入 tokens 偏大。**
   $0.005/轮；输入 4284 tokens/轮 vs 输出 170 tokens/轮（25:1）。若成本敏感，可从 chunk 数量/长度入手。

6. **延迟长尾明显，且不只由输出长度决定。**
   最慢一轮 28.6 s（输出仅 204 tokens），而输出 368 tokens 的一轮为 21.5 s
   → 服务端抖动（首包 4.2–5.1 s）对长尾的贡献不低于内容长度。

7. **短期记忆在事实通道上可判定、有损；约束通道尚不可判定（2026-10-01，见 5.9）。**
   20 个 case × 3 组：事实保留率 A **0.700** / B 0.000 / C **0.950**，
   净增益 +0.70；A 与 C 的 CI 不重叠 → **L4 确实有损**，而 A 组 L4 保真度 0.80，
   说明信息大多在摘要里却没用上，瓶颈在「注入后的使用」。
   约束通道 C(0.55) 与 A(0.25) 的 CI 重叠，**无法判定**；
   且 C 组自身只有 0.55 —— 指令逐字在上下文里也只有一半被遵守，该指标天花板偏低。
   → 用 5 个 case 时曾得出「L4 保不住指令」的结论，扩样本后被推翻，见 5.9.4 结论 3。
8. **L4 摘要有硬容量上限（2026-10-01，见 5.9.4 结论 4）。**
   `_compress_rounds` 目标是 ≤150 字；每 case 植入 4 条编号时保真度从 1.000 塌到 0.125，
   摘要把编号压成「（编号 1 等）」。**用户一轮内给出的标识符越多，L4 丢得越多。**
   → 结构化标识符（编号、单号、参数）应优先由长期记忆承载，不能只依赖有损摘要。

9. **辅助 LLM 调用点曾集体漏传 `LLM_EXTRA_BODY`（2026-10-01，见 5.9.5）。**
   压缩 / 记忆抽取 / skill 三处没走统一入口，在默认开启思考的模型上会静默拿到空 `content`
   并降级，而非报错：表现为 L4 间歇性完全缺失（修复前 5 个 case 里 1 个彻底没有摘要，
   保真度 0.80；修复后 20/20 都有摘要）。
   已用 `infra/llm.with_extra_body()` 统一收口。

## 7. 局限与注意事项

**数据集**
- Ground truth 为**自动生成**（LLM 依据单个 chunk 出题，`relevant` = 该 chunk 的源文件），**非人工标注**；
  存在与真实用户提问分布不一致的风险。
- 文档级二值相关，未做 chunk 级或**多文档**标注（见第 4.3 / 6.4 节）。
- 单 KB、单轮、无多跳问题；**未覆盖**拒答、越权访问、prompt 注入等场景。

**方法**
- 端到端为**进程内直调**，未经过 HTTP（无 JWT / 限流 / SSE 封帧）；这些不影响被测指标。
- **记忆层**：单轮评测（第 4 / 5.3 / 5.8.4 节）**不传 `conversation_id` / `user_id`**，
  因此那些数字不含 L1 / L2 / L4 的开销，生产实际会更高。
  该缺口已由 **5.8.9**（开启记忆层 + 实测成本 ≈ **+120 ms TTFT**）与
  **5.9**（短期记忆 A/B/C 效果评测）补上。
  仍需区分「评测关闭」与「生产关闭」：`start_local.bat` 与 `backend/.env` 现已接入
  Redis（`REDIS_URL=redis://127.0.0.1:6379/0`），长期记忆开关也一直默认开启
  （`memory_auto_extract = true`、`memory_maintenance_enabled = true`、
  `memory_window_size = 10`、`memory_compression_batch = 5`）。
  注意 5.8.9 / 5.9 是在 `MEMORY_WINDOW_SIZE=2` 下做的（为了在小样本里触发压缩），
  生产默认窗口 10，L4 触发更晚、成本更低。
- **长期记忆（L1/L2）的效果仍是盲区**：5.9 为隔离短期记忆而关闭了 `MEMORY_AUTO_EXTRACT`，
  所以「抽取质量」「跨会话召回」「记忆隔离在端到端层面的表现」「敏感信息误记率」都还没测
  （仅单测覆盖了机制）。这是下一步。
- 评委与被测 agent **同族模型**（均为 `glm-4-flash`），存在自我偏好（self-preference）风险；
  已用 `temperature = 0` 降低波动，但结论宜用更强模型复核。
- 检索延迟 `embed` 存在上游抖动离群点（4563 ms），**mean / max 不代表常态**，应以 p50/p90 为准。
- 第 5.8 节的对照同样受**跨模型评委**问题影响：切换后 agent 与评委都变成 `deepseek-flash`，
  因此 5.8.4 表中第 2 列不可与第 1 列比较，只有第 4 列（原评委重打分）可用。
  严格做法仍是「同一批答案交给多个评委」——本次只做了两个方向中的一个（未反向补测
  `glm-4-flash` 的答案由 `deepseek-flash` 打分那一格）。
- 两个端点的**服务端排队抖动**都很大：同一请求实测 TTFT 在 249 ms ↔ 3561 ms 之间波动，
  故本轮以 p50 + 同题集对照为主，未对单点 max 做因果归因。

**配置解读**
- `precision@3 / @5` 在本数据集（每题 1 个相关文档 + 文档级去重）下**上限即为 0.333 / 0.200**，不可直接横比。

## 8. 复现方式

```bash

backend\.venv\Scripts\python.exe -m eval.run_eval ^
    --n 50 --gen llm --repeat 3 --limit 5 --top-k 1,3,5 --rebuild-dataset

# 端到端层：默认复用上面产出的数据集（50 轮 + LLM 评委）
backend\.venv\Scripts\python.exe -m eval.run_agent_eval

# 快速冒烟（不重建数据集，只跑前 10 题）
backend\.venv\Scripts\python.exe -m eval.run_agent_eval --max-items 10

# 短期记忆效果评测（多轮，5 case × 3 组 A/B/C；需 Redis 与 .env 的 REDIS_URL）
```

> 每个 case 的会话与 Redis key 在该 case 结束时清理。

## 9. 附录：指标定义

**检索质量**（文档级二值相关，排序去重到首次出现）

| 指标 | 定义 |
| --- | --- |
| `recall@k` | top-k 中命中的相关文档数 / 相关文档总数 |
| `precision@k` | top-k 中相关文档数 / k |
| `hit@k` | top-k 中至少有 1 个相关文档则为 1，否则 0 |
| `nDCG@k` | 二值相关下的归一化折损累计增益 |
| `MRR` | 第一个相关文档排名的倒数（1/rank），取均值 |

**延迟统计**：`mean` / `p50` / `p90` / `p95` / `min` / `max`，
分位采用线性插值（与 numpy 默认一致）。

**端到端专属**

| 指标 | 定义 |
| --- | --- |
| TTFT | 从发起请求到首个 `token` 事件的时间（首 token 延迟） |
| 末 token | 从发起请求到最后一个 `token` 事件的时间 |
| 流式生成 | 首 token → 末 token，即真实的解码窗口（见 5.7） |
| 流式后收尾 | 末 token → 流式结束（图收尾 / 落库），实测 ≈1 ms |
| 检索段 | `t0 → tool_end(search_kb)`，即检索 + rerank 的墙钟耗时 |
| 生成段 | `tool_end →` 流式结束 |
| 引用命中率 | `sources`（agent 实际引用的文件名）是否包含标准答案文档 |
| 忠实度 | LLM 评委 1-5 打分 / 5：答案的事实性陈述是否均可回溯到检索资料 |
| 正确性 | LLM 评委 1-5 打分 / 5：答案是否准确、完整地解答了问题 |
| 正确率 | `correctness ≥ 0.6` 的题目占比 |
